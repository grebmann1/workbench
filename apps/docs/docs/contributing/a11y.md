# Accessibility Conventions

Workbench targets **WCAG 2.1 AA**. This page documents the repo-wide conventions for keeping UI changes accessible — use it as the checklist before a PR touching any template.

---

## Shared utilities — use these, don't re-invent

Three shared modules exist for a11y plumbing. If you find yourself implementing a live region, a focus trap, or a keyboard-shortcut listener from scratch, you're doing it wrong.

### `host-api/announce` — screen-reader announcements

```ts
import { announce } from 'host-api/announce';

announce('Row 1 added');                            // polite
announce('Session expired', { assertive: true });   // interrupts
```

Use for any non-focus-triggered state change that a sighted user sees (toast, inline banner, row insertion, step advance). Messages are deduped within a 500 ms window — repeated calls with the same string are dropped so screen readers aren't spammed.

The actual live-region DOM is owned by `component/a11y/liveRegion/`, mounted once at the app shell level. You never touch that component directly.

### `component/slds/focusTrap` — modal focus containment

```ts
import { createFocusTrap } from 'slds/focusTrap';

connectedCallback() {
    this.trap = createFocusTrap(this.template);
    this.trap.activate();
}
disconnectedCallback() {
    this.trap?.deactivate();
}
```

Wraps Tab and Shift+Tab between the first and last focusable element inside the given root. On `deactivate()`, focus is restored to whichever element was focused when the trap was activated. Esc is **not** intercepted — if your modal should close on Esc, register your own handler.

### `host-api/shortcuts` — shortcut registry

```ts
import { registerShortcut } from 'host-api/shortcuts';

connectedCallback() {
    this._unregister = registerShortcut({
        id: 'skills.close',
        keys: 'Escape',
        label: 'Close skills panel',
        scope: 'Agent',
    });
}
disconnectedCallback() {
    this._unregister?.();
}
```

**Registering a shortcut does NOT attach an event listener.** Your component keeps its own listener — the registry is a data layer. It powers two things:

1. The shortcuts-help modal (`component/a11y/shortcutsHelp/`) — users press `?` or `Cmd/Ctrl+/` to see every active shortcut.
2. `aria-keyshortcuts` attribute hygiene — the element that owns the listener should also carry `aria-keyshortcuts="<keys>"` so assistive tech announces the shortcut.

Shortcut `keys` use the [W3C aria-keyshortcuts syntax](https://www.w3.org/TR/wai-aria-1.2/#aria-keyshortcuts): `Control+Shift+S`, `Alt+F4`, `Escape`, `?`. Modifier order is Meta, Control, Alt, Shift, then the key. Multiple combos separated by spaces: `Control+/ Meta+/`.

## Templates — patterns the repo expects

### Buttons, icon buttons, inputs

Every interactive element MUST have an accessible name. In order of preference:

1. Visible text content inside `<button>`.
2. `label="..."` on `<lightning-button>` / `<lightning-input>`.
3. `alternative-text="..."` on `<lightning-icon>` / `<lightning-button-icon>`.
4. `aria-label="..."` as a last resort on raw `<button>` / `<div onclick>`.

For icon-only buttons that also need visual clarity, nest a hidden span:

```html
<button class="slds-button slds-button_icon" aria-label="Search fields">
    <lightning-icon icon-name="utility:search" size="x-small" aria-hidden="true"></lightning-icon>
</button>
```

### Links that open in a new tab

Announce it as part of the accessible name:

```html
<a href="..." target="_blank" rel="noopener noreferrer">
    Documentation<span class="slds-assistive-text"> (opens in new tab)</span>
</a>
```

### Disclosures (expand/collapse)

```html
<button aria-expanded={isOpen} aria-controls="reasoning-panel-42" onclick={toggle}>
    Reasoning
</button>
<div id="reasoning-panel-42" lwc:if={isOpen}>...</div>
```

Call `announce('Reasoning shown')` / `announce('Reasoning hidden')` on toggle if the disclosure isn't next to focus.

### Landmarks on the page shell

- `<header role="banner">` once.
- `<main role="main">` once.
- `<footer role="contentinfo">` once.
- `<section role="region" aria-labelledby="...">` for logical groupings inside a page.

### Live regions for dynamic content

Don't add your own. Use `announce()`. The shell already hosts polite + assertive regions.

### Lists, trees, grids

- Vertical lists of items: `<ul role="list">` + `<li role="listitem">` (even if SLDS styling makes them look like tiles).
- Tree navigation (SOQL fields, metadata types): `role="tree"` + `role="treeitem"` + `aria-expanded="true|false"` on branches. See `component/slds/fileTree/` for the canonical pattern — expose `@api treeAriaLabel`.
- Data tables: prefer `lightning-datatable` — it handles `role="grid"` internally. For custom `<table>`, add `role="grid"` + `role="row"` + `role="columnheader"` + `role="gridcell"`.

### Focus management for modals

Every modal uses `createFocusTrap` (see above). Do NOT hand-roll Tab handling.

## Keyboard shortcuts — how to add a new one

1. Attach your keydown listener as you normally would (document, element, capture, scoped — whatever's right for the behavior).
2. Call `registerShortcut(...)` in `connectedCallback`, unregister in `disconnectedCallback`.
3. Add `aria-keyshortcuts="<keys>"` to the element users will focus to invoke it. If the shortcut is global, put the attribute on the component root.
4. Test with the `a11y-shortcuts.spec.ts` extension spec — it asserts that every known shortcut's listener is still registered and reachable from source. Add yours to the assertion list.

## Validation

1. **Before commit**:
   - `npm run lint` + `npm run build:shared` must be clean.
   - No new `console.warn` about unresolved `host-api/*` specifiers in the extension boot.
2. **Automated a11y tests** (extension project):
   - One Playwright spec per Tier-1 surface at `packages/tests-e2e/tests/extension/a11y-<surface>.spec.ts` asserting **zero critical or serious** axe violations.
   - The Tier-2 smoke spec (`a11y-tier2-smoke.spec.ts`) asserts zero critical violations across every routable application.
   - Run: `E2E=1 npm run test:e2e:ext -- --grep=a11y`.
3. **Manual walk** (ChromeVox / VoiceOver):
   - Tab through your surface from the top — focus must be visible on every interactive step.
   - Trigger a dynamic change — confirm the screen reader announces it.
   - Open any modal your surface introduces — Esc closes, Tab cycles inside, focus returns to the opener on close.

## Rules disabled in axe (documented noise)

Three axe rules are disabled on a handful of specs because lightning-base-components render shadow-DOM structures that axe's walker can't trace through:

- `aria-required-children` (on `lightning-vertical-navigation`)
- `aria-required-parent` (same)
- `button-name` (on `lightning-button-icon` — its inner `<button>` uses `aria-labelledby` to a sibling shadow node)

These are filed in `docs/a11y-follow-ups.md`. Do **not** disable additional axe rules without adding a corresponding follow-up entry explaining why.

## When in doubt

- **Don't guess ARIA.** If a pattern isn't in this page, check the W3C [ARIA Authoring Practices Guide](https://www.w3.org/WAI/ARIA/apg/) and match the closest pattern there.
- **Prefer native semantics over ARIA.** `<button>` beats `<div role="button">` every time.
- **Run axe.** The Tier-1/Tier-2 specs catch the obvious mistakes; your PR should add to them when adding a new surface.
